# `effects` — Blam contrails, decals, effects, particle systems, weather, player feedback

Retail Halo PC `halo.exe` 1.0.10, `0x44c800 .. 0x53fc80` (124 Ghidra functions), plain C /
MSVC 7.1 / x86. Every file in this directory is one function, rewritten from its Ghidra
decompilation against `types/effects.h`, with the original decompile preserved verbatim at the
bottom of the file inside `#if 0 ... #endif` for diffing.

Gate: `python tools/build_check.py effects` -> **111 ok, 0 failed** (and `python
tools/build_check.py` -> **1500 ok, 0 failed** for the whole tree). The header's negative-array
and `offsetof` assertions live in `out/phase4/effects_smoke.c`, which also compiles clean:

```
C:\msys64\ucrt64\bin\gcc.exe -fsyntax-only -I types out/phase4/effects_smoke.c
```

111 of the 124 functions are here. The other 13 are misattributed and belong to other modules —
see [Misattributed functions](#misattributed-functions). Names are recorded, with per-function
confidence and the renames they contradict, in `symbols/agent_phase4_effects.txt`.

## What the module contains

Six subsystems share this address range, each with its own datum table, its own tag and its own
runtime record, plus two smaller things that have nowhere else to live yet.

| Subsystem | Range | Tag | Table | Record | What it is |
|---|---|---|---|---|---|
| contrails | `0x44c8b0`–`0x44d820` | `cont` | `0x0087abec` (0x100) + `0x0087abe8` (0x400) | `contrail` 0x44, `contrail_point` 0x38 | the ribbon of quads trailing an object marker; points are generated by distance/time, aged, and freed as they fade |
| decals | `0x44dc30`–`0x450590` | `deca` | `0x0087abe4` (0x800) | `decal` 0x38 | a polygon projected onto the structure BSP, flood-filled across neighbouring surfaces, bucketed by (layer, cluster) in the `decal_grid` game-state block |
| effects | `0x4505b0`–`0x4535b0` | `effe` | `0x0087abdc` (`effect` 0xfc) + `0x0087abe0` (`effect_location_marker` 0x3c) | `effect` 0xfc | the event timeline: each event spawns parts (objects, decals, damage, lights, particle systems, sounds) and particles at the markers of each `EffectLocation` |
| particle systems | `0x453600`–`0x455740` | `pctl` | `0x0087abd4` (0x158) + `0x0087abd8` (0x80) | `particle_system` 0x158, `particle_system_particle` 0x80 | long-lived emitters with up to four per-type states, each running its own physics procedure |
| particles | `0x455740`–`0x4566f0` | `part` | `0x0087abd0` (0x70) | `particle` 0x70 | individual sprites with sequence animation, point physics and impact response |
| weather | `0x457e20`–`0x458bf0`, `0x53f5c0` | `rain` | `0x0087abcc` (`weather_particle` 0x54) | `weather_instance` 0x9c (one element) | the scenario weather palette driving per-local-player rain/snow volumes |
| player feedback | `0x456730`–`0x457d50` | `cdmg` / `jpt!` | `0x006f1884` -> `player_effect_globals` 0x124 | `player_effect` 0xec | screen flash, camera shake, camera impulse and damage-direction indicators per local player |
| ambient colour noise | `0x53f860`–`0x53fc80` | — | `0x00746284`, 0x900 bytes | `ambient_noise_grid` | a 3x8x8 grid of vectors the weather and marker-colour path samples |

Entry points the rest of the engine calls: `effects_update_all` (`0x450aa0`),
`particle_systems_update` (`0x454000`), `particles_update` (`0x455b60`), `contrail_update`
(`0x44cb50`), `decals_update_fade` (`0x44e2b0`), `weather_update` (`0x53f5c0`), and the four
`effect_new*` creation wrappers at `0x4506d0` / `0x4507a0` / `0x450870` / `0x450980`.

The one thing that is easy to get wrong here: **Ghidra's auto-analysis named a whole family of the
`effe` functions `particle_system_*`.** They are not. `effect_new` / `effect_update` /
`effect_delete` / `effect_spawn_particles` / `effect_try_and_get` /
`effect_property_random_value` operate on the 0xfc byte `effect` record at `0x0087abdc`; the real
`particle_system_*` family operates on the 0x158 byte record at `0x0087abd4`, which has a separate
initializer and a separate tag. Both are in this directory, under their corrected names.

## Struct layouts

All of these live in `types/effects.h`; the tables below are the summary. Offsets are byte
offsets from the struct base, `#pragma pack(push,1)` is in force, and pointer fields are 4 bytes on
the target. Types that already existed elsewhere are **not** redeclared here: every `effe` / `pctl`
/ `part` / `cont` / `deca` / `rain` tag structure and `ModelCollisionGeometryBSP*` come from
`types/tags.h`, `object` / `object_header` / `object_marker` / `bsp_leaf_reference` from
`types/objects.h`, `real_point3d` / `real_vector3d` / `real_matrix4x3` / `real_plane2d` /
`projection_axis_pair` / `random_seed` from `types/math.h`, `data_array` / `datum_index` from
`types/memory.h`, `cache` from `types/cache.h` and `player_globals` from `types/game.h`.

## Known gaps

**Hidden register arguments are the dominant problem, as in every other module in this tree.** The
effects code passes output pointers and this-like records in `EAX`/`ECX`/`EDX` constantly and Ghidra
recovers almost none of them. Every such reconstruction is marked `UNSURE` in the file that makes
it; there are **349** of those markers across the 111 files. Where a register argument could be
pinned from a sibling file's established convention, or from where the callee's own writes land, it
was; where it could not, the file says so rather than inventing a plausible name.

### The six particle-physics procedures Ghidra never created

`0x4552a0` and `0x4554d0` (system update physics), `0x455310`, `0x4554e0` and `0x455610` (particle
creation physics) and `0x455350` (particle update physics) sit inside this address range, are
reached only through the three `.rdata` dispatch tables at `0x0065743c` / `0x00657444` /
`0x00657450`, and Ghidra created no function for any of them. They own
`particle_system_particle` +0x1c..+0x40 (position, `unknown_28`, direction), which is why those
three fields are the weakest part of that struct. All six were rewritten in cleanup pass 1 (see the
table at the end of this file).

### Functions that are structural skeletons, not field-by-field reconstructions

These are the ones to treat with suspicion; each says so in its own header.

### Type gaps that remain

* `particle_creation_data` (`0x5c`, "at least") has no field for the rotation rate or the initial
  spin angle. `effect_spawn_particles` rolls both, and `particle_new` is handed them in a register
  block Ghidra never reconstructed, so both rolls are computed and then discarded with a
  `TYPES-GAP` comment rather than written into an invented field. The same block is why
  `unknown_1c` (+0x1c) and `velocity` (+0x28) are assigned by declaration order, not by evidence.
* `effect_spawn_particles`'s spawn count is the difference of the distribution function evaluated
  at this tick's and last tick's event fraction. The raw code truncates each evaluation straight to
  `int16` with no visible multiply. The rewrite scales each by
  `effect.particle_counts[type_index]` because nothing else makes the "difference of two
  evaluations" produce a usable count, but **the multiply is not in the decompile**.
* `EffectPart.violence_mode` and `EffectParticle.violence_mode` (`types/tags.h`, offset 0x02) are
  tested here against the values 1 and 2 gated by `effect.flags`' `_effect_first_person_bit`, which
  matches `EffectCreate_t`'s only-in-first-person / only-in-third-person far better than a violence
  setting. The numeric comparison is the same either way, so the field is read as-is and the
  discrepancy is flagged in `effect_spawn_particles.c` and `object_change_color_evaluate.c`.
  `types/tags.h` is generated from invader's definitions and is not this module's to edit.
* `object` +0x106 and +0x41c (`effect_first_person_screen_timer_active`) are read here but are not
  part of `object` in `types/objects.h`.
* `FUN_0053ed60` (`0x53ed60`, outside this range) is the environment probe the `EffectCreateIn`
  air-only / water-only gates call. Its signature is modelled from three call sites in this module
  and it is still `FUN_`-named.
* `0x00746f9c` is `structure_bsp_globals` here, typed `uint8_t *` and indexed by byte offset
  (+0xe4 leaf table, +0x1b4/+0x1b8 weather palette). `src/objects` and `src/projectiles` declare the
  same address as `ScenarioStructureBSP *structure_bsp_tag_data`. Both readings are of the same
  object — +0xe4 is `leaves.pointer` — but the tree has not settled on one.
* Several globals this module reads are named differently by the modules that reached them first
  (`0x0068944c`, `0x006966f8`, `0x00696720`, `0x0069673c`, `0x0069c632`, `0x006b0ad8`, `0x006b145c`,
  `0x006f1884`, `0x00719ccc`, `0x007c3108`, `0x007c3110`, and the six datum-table pointers
  `0x0087abcc`–`0x0087abe0`). Inside `src/effects` every address now has exactly one name and one
  type; the cross-module divergence is not resolved, and in most cases the other module's name is a
  `DAT_`-shaped placeholder while this module has the initializer that proves the type.
